Notes

Build notes, not a highlight reel.

Short, honest write-ups on decisions I made building HostelMania — including the ones I'd make differently now. I'd rather show the reasoning than just the result.

Architecture 2025

Why MySQL, not MongoDB, for HostelMania's order data

Food ordering is fundamentally relational: a student belongs to a hostel, an order belongs to a student and a menu item, and a payment belongs to an order. Every one of those relationships needed to stay consistent — an order should never reference a menu item that's been removed, and a payment should never exist without a matching order. That's exactly the kind of integrity foreign keys and transactions are built for, and it's the kind of thing you have to re-implement by hand in a document store.

MongoDB would have been the trendier choice, and I considered it early on. But I wasn't building something with unpredictable, evolving document shapes — I was building something with a small, stable set of entities and strict rules about how they relate. The interesting design problem wasn't schema flexibility, it was correctness — making sure a canceled order can't silently still show as paid, that kind of thing. MySQL made that the default behavior instead of something I had to build myself.

Bug 2025

The auth bug that taught me not to trust client-side role checks

Early in HostelMania, the staff dashboard link was simply hidden from students via CSS and a client-side if (role === 'staff') check in the UI. It worked, in the sense that students never saw the button. It did not work in the sense that mattered — the actual API endpoint behind that button had no idea who was calling it. Anyone who found the URL, or opened dev tools and hit the endpoint directly, could have called it.

Nothing bad happened, because I caught it before it went anywhere near real users — but it's the kind of mistake that's invisible until you specifically go looking for it, because the UI itself looks completely correct. Since then, my rule is simple: the UI hides options, the server enforces them. Every role-gated route in the backend now re-checks the session role independently of whatever the frontend already decided to show. It's a small habit, but it's the one bug from this project I think about the most.

Retrospective 2025

What I'd rebuild in HostelMania if I started today

Two things, honestly. First, I'd write tests for the order-status transitions before writing the transitions themselves. I didn't, because it was a solo project on a semester deadline and testing felt like overhead I couldn't afford — but I ended up manually re-testing the same order flow by hand every time I touched that code, which was slower in total than just writing the tests once would have been.

Second, I'd separate the payment confirmation logic from the order-update logic much earlier. I built them tangled together because it was faster in the moment, and then spent real time later untangling them so a failed payment couldn't leave an order in a half-updated state. Both of these are the same lesson wearing different clothes: the shortcut that feels fast on day one is rarely the one that's still fast on day thirty. It's a lesson I now try to apply before I need to re-learn it on the next project.
